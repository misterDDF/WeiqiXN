# WeiqiXN UnityProject 规格说明

## Scope

**范围**

- 本文档记录 Unity 围棋项目当前已经实现的系统行为。
- 本文档覆盖启动流程、本地对局流程、棋盘配置、落子处理、提子校验、场景与 UI 入口、存档行为和当前依赖。
- 本文档不定义联机计划、架构理由或阶段路线；这些内容分别归属 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [ROADMAP.md](ROADMAP.md)。

## Current Behavior

- 2026-06-09: Duel voice prompts are routed through `GameAudio` and `DuelAudioSystem` in addition to the existing BGM and stone SFX paths. `GameAudio` owns a dedicated voice `AudioSource` and loads duel voice clips from `Assets/Audio/Voice/OgsPreview/*.wav`; these clips are declared in `runtime_asset` for player AssetBundle builds. `DuelAudioSystem` plays a once-per-duel game-start cue, pass cue on accepted pass events, OGS stone-removal cue when entering stone-removal phase, game-end winner/tie cues, byoyomi start/period cues, and final 10-second countdown cues only for the current local/input side where a local side is known. Countdown number voice is lower priority than other duel voices: if the voice channel is playing or still inside the short voice-throttle window, the current countdown second is skipped instead of interrupting, delaying, or replaying it, while non-countdown duel voices may interrupt a previously started countdown number. Hold-time countdown voice is suppressed when byoyomi is configured, so hold-time countdown voice only plays for time settings that have hold time without byoyomi. Byoyomi count prompts are still marked announced only after playback actually starts, so short voice-throttle windows can retry those prompts instead of permanently skipping them. The current `OgsPreview` wave files are Mandarin Chinese preview clips: most are sliced from Online-Go.com `zh-cn-inni` audio sprites, while `StartCounting.wav` and `Byoyomi.wav` are local Microsoft Huihui Desktop TTS replacements for "开始读秒" and "读秒"; all can be replaced by alternate final voice files with the same filenames.
- 2026-06-09: OGS shape/ownership preview keeps OGS server handicap data separate from local `duel_handicap` placement. `OgsDuelSystem` caches server `komi` from `gamedata` / terminal payload into `SceneComponentOgsDuel`, and KataGo ownership requests in `OgsDuelScene` use that server komi instead of falling back to local `SceneComponentDuel.handicapCfgId`. The white-points text in the shape panel labels OGS games as `（让子）` when server handicap / initial stones / free-handicap opening placements indicate handicap stones, labels `（让先）` when the server komi is `0.5` without handicap stones, and otherwise keeps the normal `（贴目后）` label. OGS friend challenge creation now sends the selected `duel_handicap` row's `komi` together with its handicap count, so Unity-created OGS friend games preserve the selected even/sen/handicap komi intent before later relying on server `gamedata` as authority.
- 2026-06-04: OGS browser login keeps the desktop/Editor localhost callback path and uses an HTTPS-to-deep-link bridge on Android/iOS player builds. Mobile OGS login opens the authorization URL with `redirect_uri=https://leo-zhang-git.github.io/weiqixn-oauth-redirect/ogs/callback/`, waits for the GitHub Pages bridge to return through Unity `Application.deepLinkActivated` / `Application.absoluteURL` at `weiqixn://ogs/callback`, validates the returned OAuth `state`, and then exchanges the returned authorization code through the existing PKCE token path while keeping the same HTTPS redirect URI for OGS token exchange. Android builds register `weiqixn://ogs/callback` on the Unity launcher activity through `Assets/Plugins/Android/LauncherManifest.xml`; the OGS OAuth application must include the GitHub Pages HTTPS redirect URI in its allowed callback list.
- 2026-06-02: Main menu and duel audio are wired through `GameAudio`. `MainMenuScene` and `DuelScene` both start `Assets/Audio/BGM/Active/HappyMomentsPianoFull.ogg`; additional BGM files under `Assets/Audio/BGM/Alternatives/` are preview-only candidates and are not referenced by runtime audio code or `runtime_asset` until selected. `DuelAudioSystem` listens for `OnAfterAddChessToBoard` and `OnAfterCaptureChessFromBoard` to play one active Sabaki placement clip from `Assets/Audio/SFX/StonePlace/StonePlace_Sabaki_00..04.mp3`, the active single-stone capture clip `Assets/Audio/SFX/Capture/Capture_Single.mp3`, or the active multi-stone capture clip `Assets/Audio/SFX/Capture/Capture_Multi.mp3` when one move captures more than one stone. These code-loaded audio clips are declared in `runtime_asset` so player AssetBundle builds include them. Short stone SFX use exclusive playback with a minimum interval; capture SFX takes priority over placement SFX for the same move to avoid stacked burst volume during large captures. Audio source, author, and license records are kept in `Assets/Audio/THIRD_PARTY_AUDIO.md`.
- 2026-06-02: The main menu OGS game entry is hidden until the saved OGS session includes `write` scope, then loads an active square OGS game when one exists or opens `DuelSetupPopup` in OGS mode before starting OGS realtime automatch. During automatch the cancelable waiting popup displays `寻找对局中...`; pressing `取消` cancels the local wait and sends `automatch/cancel` when the realtime match request has already been submitted. After `automatch/start`, Unity sends `game/connect`, waits for server `gamedata`, and enters `OgsDuelScene`. `OgsDuelScene` reuses the duel board and HUD presentation but treats OGS `gamedata` / `game/{id}/move` as the only board authority. Loaded OGS games resolve the local seat from server black/white player ids across direct, nested, numeric, and top-level player-id fields. OGS array/packed move coordinates map directly to local `RectCoordinates(x, z=y)`; local submissions encode the same local `z` value as OGS y. OGS handicap handling follows server payload shape: explicit server initial-state stones are rebuilt outside accepted `moves`, saved into replay record `initialStones`, and make white the default first accepted move/input side after setup unless server current-player fields provide an explicit side, while `free_handicap_placement` games keep the first handicap-count accepted moves as same-color opening placements before normal alternation. OGS clock state is applied from `gamedata.clock` / realtime `game/{id}/clock` into the duel HUD; Unity may estimate visible countdown between server clock snapshots but does not locally adjudicate OGS timeout. When OGS sends official `clock.start_mode`, the HUD displays the start clock from `expiration` / `expiration_delta` for the current first-move player and does not consume normal `black_time` / `white_time` thinking time until OGS leaves start mode. OGS finished-state handling maps server result fields such as `outcome`, `winner`, `black_lost` / `white_lost`, `result`, `reason`, and termination-style fields into the existing `DuelPage` `GameEnd` display: resignation writes `resignLoserGuid`, timeout writes `timeoutLoserGuid`, score/points writes score margin, and unrecognized server terminal reasons conservatively fall back to score display with diagnostic logging. OGS `paused` / `suspended` phase locks local command submission without changing black/white seat mapping. OGS bot games disable takeback and ignore `undo_requested` messages without showing a peer-confirm popup; non-bot OGS games keep the realtime undo request/accept/cancel path. OGS resign is server-backed, shape/ownership remains available, local score request is disabled, local AI analysis/recommendation is disabled, and accepted OGS moves/passes are written through the local replay archive with `sourceType=ogs`.
- 2026-06-08: OGS stone-removal scoring is driven only by server phase and realtime payloads. Unity does not show local "正在数子" from consecutive OGS passes until OGS explicitly enters `stone removal` / `stone_removal`. In that phase ordinary move/pass input is locked, the normal manual ownership button is repurposed as `确认死子` / `等待对方确认`, the pass button is repurposed as `不接受`, and the settings-panel local score request remains disabled. Clicking `不接受` first opens a confirmation popup with `您确定拒绝数子并返回对局吗？`; confirming then sends `game/removed_stones/reject`. The stone-removal timeout is displayed as a separate text below the confirm button; it is read only from the OGS clock stone-removal timeout (`stone_removal_expiration` / `stoneRemovalExpiration`, with OGS's stone-removal `expiration` fallback when the clock pause state is stone-removal, or server-provided `stone_removal_time_left` / `stoneRemovalTimeLeft`) and shows `--:--` when those fields are absent. Clicking an unremoved live stone sends `game/removed_stones/set` for that whole same-color connected string with `removed=true`; clicking an already removed stone sends the same realtime command with `removed=false`. Local clicks do not mutate the authoritative removed-stone set; Unity updates dead-stone state only after OGS `game/{id}/removed_stones` or `gamedata` removed-stone data is applied. Removed stones keep their `ChessInfo`, entity, renderer, and move history intact, but their existing stone renderers switch to the same translucent material used by that color's preview stone; clearing removed state restores the original stone materials. A red cross is only a hover preview for unremoved stones during stone-removal phase and is not stored as board state. Entering stone-removal and each server removed-stone update automatically refresh ownership preview from a temporary current-board snapshot that excludes the server-marked removed stones, without deleting or editing `SceneComponentChessBoard.chessInfoDict`; this automatic OGS preview only draws the board overlay and does not open the ordinary ownership black/white local-points panel. Exiting stone-removal or reaching `finished` clears the preview. Accept sends `game/removed_stones/accept`; final scoring and `GameEnd` still wait for OGS `finished` / score payload and never use local ownership preview as the official result.
- 2026-06-05: Incoming OGS friend challenge invites are polled from the main menu whenever an OGS session exists. Opening `MainMenuPage`, completing OGS login, and refreshing the saved OGS account request an immediate invite poll; accepting an invite still requires a write-capable OGS session because the accept endpoint mutates server state.
- 2026-06-02: Full OGS diagnostic payload logging is available only when `LoggerConfig.ENABLE_OGS_VERBOSE_LOG` is set to `true`. In that mode OGS HTTP responses and realtime websocket sent/received payloads are written to logs, with token/JWT/authorization-style fields redacted.
- 2026-05-29: `ReplayScene` keeps the desktop replay camera horizontal offset only when the current view is not portrait, using the same `height > width` portrait judgment as UI layout. Portrait replay uses the same board-centered camera framing as the base chess-board camera, so narrow screens do not shift the board sideways for desktop HUD spare space.
- 2026-05-29: KataGo Human SL is part of the local runtime contract. `game-config.json` now configures both the normal analysis model (`katago.model.fileName`) and the Human SL companion model (`katago.model.humanSlFileName`, default `b18c384nbt-humanv0.bin.gz`). Windows exe startup passes the companion model through `-human-model`; Windows and Android native startup use the bridge export `kg_create_engine_with_human_model`. Android runtime preparation and editor build validation/copy require both model files. AI duel difficulties that enable `useHumanPolicy` send `overrideSettings.humanSLProfile` with `ignorePreRootHistory=false`, request policy output, and use `humanPolicyWeight` to decide how often KataGo `humanPolicy` is sampled before falling back to normal `moveInfos`/`policy`.
- 2026-06-09: Android native KataGo startup avoids known unsafe OpenCL tuning devices. When CPU fallback is enabled, devices whose Android build fields identify a MediaTek Dimensity-class SoC (`Dimensity`, `mt68*`, `mt69*`, `k68*`, `k69*`) skip `katago_bridge_opencl` and start `katago_bridge_eigen` directly. For other Android devices, an uncached OpenCL startup writes `KataGoData/opencltuning/weiqixn_opencl_tuning_attempt.marker` before entering KataGo; a later startup that finds this marker without any `tune*.txt` cache skips OpenCL and falls back to eigen. Successful OpenCL startup clears the marker after tuning cache is generated or reused and smoke validation passes. This fallback does not remove the intended first-run OpenCL autotuning path on devices that are not known unsafe and have no failed tuning marker.
- 2026-05-29: `ReplayPage` exposes the same "形势" button style used by `DuelPage`; it analyzes the current replay board snapshot, draws ownership overlay, displays a small black/white point result panel using the replay record komi, can be toggled off independently, and is canceled when the replay cursor, try-mode state, or replay scene changes. `DuelPage` exposes the same icon-only "AI分析" button style used by `ReplayPage`; in non-LAN duels it runs the same three-tier AI recommendation analysis and ownership rendering pipeline as replay AI analysis, while LAN duels hide this button. Replay and duel AI recommendation rendering share the same `replay_config` tier/candidate/winrate display parameters and the same local legality filtering before drawing recommendation markers. The manual "形势" overlay and user-triggered AI analysis overlay are mutually exclusive at the UI entry point: opening one first closes or cancels the other, so their selected states and ownership drawings do not coexist.
- 2026-05-28: UI pages are not cached as hidden GameObject instances after close. Closing a page removes it from its `UIContext` and destroys the page GameObject; reopening a page creates a fresh instance, reloads the prefab, and runs the full loaded/open lifecycle so popup ordering and default selection state do not depend on a time-based cache window.
- 2026-05-28: `DuelSetupPopup` persists the latest setup selection independently for local duel, computer duel, and LAN room setup in the user save when the popup closes. Reopening the popup loads the matching mode preference, validates saved config ids against current tables, and falls back to the default setup for invalid or missing values.
- 2026-05-28: KataGo analysis requests now support scoped retry behavior. Default requests retry once after restarting the active backend; AI-duel move analysis and user-triggered replay AI recommendation analysis keep retrying recoverable empty/timeout-style failures until their scene/request scope is canceled. Leaving `DuelScene` or `ReplayScene` cancels the corresponding retry scope, and stale replay AI requests are still invalidated by `aiAnalysisVersion` when the user changes cursor, try-mode state, or closes recommendations. Android analysis waits for foreground before starting a request when the app is already backgrounded and adds a bounded background grace window to native bridge timeouts so a short background switch does not consume the normal foreground analysis timeout. Android keep-awake leases also temporarily enable `Application.runInBackground` while active and restore the previous value when the last lease is released; foreground screen sleep behavior remains unchanged.
- 2026-05-29: Native KataGo analysis uses one cross-platform request scheduler for Windows and Android native backends. `game-config.json` sets `katago.analysis.maxConcurrentNativeRequests`; Unity requests that value for native backends and caps to `1` when the loaded bridge binary does not expose concurrent-analyze support. `KataGoBootstrap` owns the queued request priority and only dispatches up to the active concurrency window into KataGo; queued higher-priority requests, such as replay AI recommendation analysis, are selected before lower-priority background chart requests the next time a slot opens, while requests already sent into KataGo are not canceled for preemption. Queued requests can also carry an owner key so a scene or subsystem can clear only its own not-yet-dispatched requests during teardown without clearing newer scene requests or active KataGo work. The native bridge routes concurrent `kg_analyze` calls by request id on the single active analysis engine instead of letting callers consume the shared output queue directly. The current shared OpenCL analysis configuration targets two simultaneous positions with `numAnalysisThreads=2`, `numSearchThreadsPerAnalysisThread=4`, and `nnMaxBatchSize=16`; Windows runtime DLLs and both Android native plugins have been rebuilt with this bridge protocol.
- 2026-05-29: Mobile player builds disable replay chart high-precision self-refresh requests. Android and iOS builds still keep loading samples and low-precision background fill, but they do not start the full-chart high refresh pass or the retrying current-cursor high-precision chart repair request. User-triggered replay AI recommendation analysis remains allowed to write its returned `rootInfo.winrate` / `rootInfo.scoreLead` back into the current mainline chart point, so the currently analyzed move can still receive a high-visit chart value without separate chart requests competing with AI recommendation analysis.
- 2026-05-28: Replay chart generation keeps bounded behavior. Loading samples and HUD background fill use single-attempt chart point analysis; `ReplaySystem` may enqueue all missing chart-point analysis tasks with a replay-scene owner key, and the shared KataGo request scheduler decides how many are actually dispatched at once according to the active backend concurrency configuration and request priority. Leaving the replay scene cancels the scene token and clears any not-yet-dispatched queued requests with that owner key, but it does not cancel requests that have already entered KataGo. If background chart generation fails or times out, it stops at that move and records a pending status instead of retrying the full chart indefinitely. When the user later moves the main replay cursor to a chart point that is still missing and no higher-priority replay AI analysis/loading chart job is active, `ReplaySystem` starts a current-cursor chart repair request. That visible chart repair retries while the user remains on the same mainline cursor and stops when the cursor changes, try mode is active, the point succeeds, or the replay scene exits. User-triggered replay AI recommendation analysis takes priority over current-cursor chart repair: starting AI analysis cancels pending current-cursor chart repair, but background chart fill may continue; queued background chart requests remain lower priority than AI requests, and already-dispatched chart requests are not canceled for AI preemption. After AI analysis ends, chart fill or current-cursor repair may resume if still applicable.
- 2026-05-27: UI pages force their root `CanvasScaler` reference resolution during runtime load: Unity Editor defaults to the PC `1600x900` profile and can be overridden by the ignored local `UserSettings/UIRuntimeCanvasResolution.json` editor preview config, PC builds use `1600x900`, and Android and iOS player builds use portrait `720x1280`. This runtime rule overrides any preview `referenceResolution` saved on page prefabs.
- 2026-05-28: Duel board input uses a shared UI pointer hit check that covers both mouse pointers and touch `fingerId` pointers before showing preview stones or submitting board clicks, so modal UI such as `ConfirmPopup` blocks Android touch-through board input. Duel move submissions carry the submitting player flag and the local authority layer rejects submissions that do not match the current turn. Take-back and resign confirmation popups capture their opening move-count and turn context; if the position changes before confirmation is applied, the stale confirmation is rejected instead of applying to the new turn.
- 2026-05-28: Editor build menus keep the existing Development PC and Android entries and also provide non-Development variants: `自定义功能/打包/打PC包(非Development)` and `自定义功能/打包/Build Android APK (Non-Development)`. The non-Development entries share the same asset bundle, KataGo runtime validation/copy, IL2CPP, orientation, and output-path setup as the existing entries, but omit `BuildOptions.Development`.
- 2026-05-28: Android player builds use a project launcher manifest that removes `WRITE_EXTERNAL_STORAGE`, `READ_EXTERNAL_STORAGE`, and `READ_PHONE_STATE` during manifest merge. Current Android runtime data paths use app-private storage through `Application.persistentDataPath`, so the built APK keeps only the required `INTERNET` permission.
- 2026-05-26: Android startup Loading progress is mapped as one continuous first-launch flow: KataGo runtime file preparation displays from 0% to 12%, KataGo native warmup displays from 12% to 98%, and the initial main-menu scene load displays from 98% to 100%. Android OpenCL native warmup uses a 120-second interpolation estimate for its first initialization/tuning phase, and first-run autotuning may generate and persist a local OpenCL tuning cache under `KataGoData/opencltuning`; the displayed percentage is still an estimated startup interpolation, not KataGo-native fine-grained tuner progress.
- 2026-05-26: Android startup and duel scenes keep the screen awake while the app remains in the foreground by applying `Screen.sleepTimeout = NeverSleep` through a small runtime keep-awake lease. `Startup` holds the lease during resource prep, runtime preparation, KataGo warmup, and the final scene transition; `Duel` holds the lease during an active duel. When Loading closes, when a scene exits, when the app loses foreground focus or is paused, or when the app quits, the lease is released and the previous sleep timeout is restored. This behavior is Android-only and does not change the project-wide default sleep setting on other platforms.
- 2026-05-25: Windows `native` KataGo backend now mirrors the `exe` backend fallback shape. `game-config.json` uses `katago.windows.nativeOpenClEngineName` for `native-opencl` and `nativeCpuEngineName` for `native-eigen`; with `preferOpenCl=true` and `allowCpuFallback=true`, runtime tries `native-opencl/katago_bridge.dll` with `analysis_example.cfg` first, loads the bridge by full DLL path, requires the bridge to self-report `opencl`, logs candidate name, DLL/config/model paths, bridge backend, and exception details on skip or failure, then falls back to `native-eigen/katago_bridge.dll` with `analysis_nowrite.cfg` and a required `eigen` backend match. Windows native player builds still exclude `katago.exe`; when CPU fallback is enabled, `native-eigen` is required and incomplete `native-opencl` only produces a build warning. `exe` and `native` now share one startup interpolation model in `KataGoBootstrap`; the native DLL path runs blocking startup and smoke-test operations through the same timed loading progress refresh instead of freezing at a candidate boundary.

### 2026-05-15 Current Addendum

- 2026-05-25：仓库根目录新增 `game-config.json` 作为 KataGo 后端选择配置。`katago.backend.windowsEditor` 和 `katago.backend.windowsPlayer` 支持 `exe`、`native` 或 `disabled`；当前 Windows 默认已切为 `native`。`androidPlayer` 和 `iosPlayer` 字段先预留为 `native` 方向，非 Windows 运行时仍会跳过本地 KataGo 启动。Windows 原生后端使用 `KataGo/engines/win-x64/native-eigen/katago_bridge.dll`，通过 P/Invoke 调用同一套 analysis JSON 请求/响应合同，并使用 `analysis_nowrite.cfg` 和仓库模型文件。Windows PC 构建成功后会把根目录 `game-config.json` 复制到包体根目录；构建前会按 `windowsPlayer` 选择校验 exe 运行资源或 native bridge 运行资源。`native` 打包只复制 `native-eigen/`、当前模型和 `game-config.json`，不会把 `opencl/`、`eigenavx2/` 或 `katago.exe` 打进包体；`exe` 打包保留完整 `KataGo/` runtime 复制行为。

## Fixed Rules

**固定规则**

- 本地对局是当前行为基线。
- 棋盘坐标使用矩形网格坐标，字段为 `x` 和 `z`。
- 棋盘位置索引公式为 `z * gridSize + x`。
- 玩家标记通过 `DuelUtils.GetGamePrefabTypeIdWithPlayerFlag` 映射到黑白棋子预制体。
- 对局记录文件中的 KataGo 标准 `moves` 是保存侧的棋谱输出；场景存档不再保存 `SceneComponentChessBoard.chessInfoDict`。
- `chessInfoDict` 和 `lastChessInfoDict` 跳过保存检查，只作为运行时棋盘缓存和局面对比状态。
- 非法落子不显示预览棋子，页面不额外弹出“无法落子”提示；真实落子被规则拒绝时系统仍保留 `OnDuelMoveRejected` 边界事件。
