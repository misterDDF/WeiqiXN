# 架构迭代计划表

## 文档定位

本文是 [ROADMAP.md](../ROADMAP.md) 的阶段执行明细，用于把当前架构体检结论拆成可推进、可验收的迭代项。

- `ROADMAP.md` 仍是阶段目标、范围和非目标的权威来源。
- 本文只记录阶段内执行顺序、交付物、验收口径和风险控制。
- 当阶段目标、范围或联机路线发生变化时，先更新 `ROADMAP.md`，再同步调整本文。

## 推进原则

- 按阶段推进：阶段内连续处理同一主线，阶段结束后统一收口文档、验证和剩余风险。
- 本地对局是回归基线：任何规则、AI、存档或联机准备改动都不能破坏本地热座对局。
- 先稳定领域契约，再扩展功能：优先收敛落子命令、规则结果、手顺、结算和保存边界。
- 当前主线不进行实际联机功能开发：不接网络 SDK、不实现传输层、不做房间/匹配/重连，只做能降低后续联机开发混乱度的结构迭代。
- 不提前引入大型框架：除非当前项目能力无法满足阶段目标，否则不新增通用 DI、完整 ECS、网络框架包装层或大规模 asmdef 重排。
- 每个阶段结束时必须判断是否需要更新 `SPECIFICATION.md`、`ARCHITECTURE.md`、`ROADMAP.md` 和对应模块文档。

## P0：规则契约与本地基线收口

### 背景

当前 `DuelMoveRule` 已经提供共享规则入口，但仍以 `SceneComponentChessBoard` 的可变状态作为输入和中间状态。`ChessBoardSystem` 负责真实落子、棋子实体创建和事件派发；`DuelAiSystem` 用同一规则入口筛选候选点；悔棋功能通过 `DuelSystem` 的手顺回放重建棋盘，也会调用同一规则入口。这个方向正确，但后续结构迭代需要更明确的领域命令和结果，避免真实落子、AI 检查和悔棋回放分叉。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P0-1 | 定义落子命令和拒绝原因 | `DuelMoveCommand`、`DuelMoveRejectReason`、`DuelMoveResult` 或等价结构 | 非当前玩家、越界、已有棋子、自杀、重复局面等原因可区分 |
| P0-2 | 收敛规则入口 | 规则方法返回“合法性、提子列表、上一局面、新局面、拒绝原因”，检查路径不保留模拟状态 | AI 候选检查后棋盘状态不变 |
| P0-3 | 调整真实落子与回放应用点 | `ChessBoardSystem` 和悔棋回放只应用 accepted result，负责实体创建/销毁和表现层更新 | 本地落子、提子、最新手标记、悔棋回放行为不变 |
| P0-4 | 增加非法落子反馈 | 系统发出非法原因事件；UI 预览只显示合法点 | `OnDuelMoveRejected` 已建立系统边界；`DuelPage` 只在合法点显示预览，不额外弹出无法落子提示 |
| P0-5 | 补最小规则测试或可重复验证清单 | EditMode 测试优先；无法测试时补清晰手动步骤 | 覆盖越界、占位、提子、自杀、简单重复、检查不污染状态、悔棋后棋盘一致 |

### 阶段退出条件

- 本地热座对局可以完成落子、提子、虚手、认输、请求数子和保存入口的手动回归。
- AI 候选合法性检查与真实落子共用同一规则路径。
- 悔棋回放与真实落子共用同一规则结果应用口径。
- 规则入口具备明确拒绝原因。
- 真实落子拒绝结果已通过系统事件暴露；当前 UI 通过合法预览控制可见反馈，不额外显示无法落子提示。
- 文档同步到 `08-board-and-rules.md`、`09-duel-flow.md`，必要时同步 `ARCHITECTURE.md`。

### P0 手动回归清单

- 本地热座对局：正常落子、提子、最新手标记；占位、自杀、重复局面位置不显示预览棋子，点击后不提交落子。
- AI 对局：AI 候选点筛选后棋盘不出现模拟残留；AI 合法落子仍通过 `OnAddChessToBoard` 进入真实落子流程。
- 回放链路：悔棋一手、AI 对局悔两手后，棋盘棋子实体、`kataGoMoves` 和当前行棋方保持一致。
- 终局相关：虚手、双方连续虚手数子、请求数子、认输和保存入口保持现有行为。
- 文档一致性：`ARCHITECTURE.md`、`08-board-and-rules.md`、`09-duel-flow.md` 与当前规则结果模型一致。

## P1：手顺、结算、存档边界收敛

### 背景

当前对局手顺直接保存为 KataGo `JArray`，ownership 查询和数子结果分散在 `DuelSystem` 与 `DuelOwnershipSystem` 中，悔棋也直接克隆和截断 `JArray` 后回放棋盘，保存流程先写记录文件和 save info，再 fire-and-forget 保存场景数据。短期可用，但后续死子确认、复盘、联机重连会放大边界不清的问题。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P1-1 | 封装手顺访问 | `DuelMoveHistory` 已集中创建、追加、克隆、截断、尾部虚手统计和 KataGo `moves` 输出 | 保存、ownership 请求、AI 查询和悔棋仍输出相同 JSON 结构 |
| P1-1a | 收敛悔棋/回放边界 | 悔棋截断和尾部虚手统计已通过 `DuelMoveHistory`，回放仍走规则结果应用口径 | 悔棋一手、AI 对局悔两手、虚手后悔棋均保持当前行为 |
| P1-2 | 收敛 ownership 查询 | `DuelOwnershipQueryService` 已集中 KataGo ownership 请求、缓存读取、阈值统计和查询失败日志 | 形势按钮、请求数子、连续虚手共用同一查询和缓存口径 |
| P1-3 | 收敛数子结果模型 | `DuelOwnershipQueryService` 统一构建 ownership 分数、贴目、胜者、目差和 `scoreSource` | UI 展示和 GameEnd 字段保持一致 |
| P1-4 | 调整保存流程 | `OnDuelSaveResult` 已暴露保存成功/失败；`GameSaveManager.SaveDataAsync` 返回保存结果并用 finally 释放保存锁和弹窗 | 保存失败可诊断；不再静默留下最终场景保存失败 |

### 阶段退出条件

- `SceneComponentDuel` 不再把 JSON 类型作为无边界业务状态扩散给多个系统。
- 悔棋、保存、ownership 请求和 AI 查询都通过同一手顺访问边界读取或输出 `moves`。
- ownership 展示和终局数子共用一套结果口径。
- 保存链路不再静默忽略最终保存失败。
- 文档同步到 `05-save-load.md`、`09-duel-flow.md`，必要时同步 `ARCHITECTURE.md` 和 `SPECIFICATION.md`。

## P2：AI 与 UI 大类拆分

### 背景

`DuelAiSystem` 已经承担 AI 回合触发、KataGo 请求、动态预算、结果解析、候选筛选、随机选点和日志诊断。`DuelPage` 同时承担棋盘输入、HUD、弹窗、结算展示和按钮可见性。继续追加功能会让维护成本快速上升。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P2-1 | 拆 AI 回合驱动 | `DuelAiSystem` 已只保留系统监听、AI 回合判断、取消检查和提交落子/虚手结果 | AI 仍在白方回合自动行棋或虚手 |
| P2-2 | 拆 AI 分析请求 | `DuelAiAnalyzeService` 已集中 KataGo AI 请求构造、probe/full 请求调度和结果元信息返回 | OpenCL/Eigen fallback 不受影响 |
| P2-3 | 拆预算策略 | `DuelAiBudgetService` 已集中棋盘尺寸参数解析、probe/full budget 决策和预算日志 | 不同棋盘尺寸预算仍按配置解析 |
| P2-4 | 拆候选选择 | `DuelAiMoveSelector` 已集中 moveInfos/policy 解析、合法性筛选和加权选择 | 难度配置行为保持一致 |
| P2-5 | 拆 UI 输入与展示 | `DuelPageBoardInputController`、`DuelPageHudView` 和 `DuelPageInteractionState` 已分别承接棋盘输入预览、HUD/面板展示和输入可用性判断 | 按钮、提示、结算面板行为不变 |
| P2-6 | 降低热路径日志 | 事件、FSM、AI 细节日志改为可控输出 | Console 不再被常规事件刷屏 |

### 阶段退出条件

- AI 和 UI 新增功能有明确代码落点。
- 行为保持不变，不引入新的玩法能力。
- 文档同步到 `03-ui.md`、`09-duel-flow.md`，必要时同步 `ARCHITECTURE.md`。

## P3：联机架构决策

### 背景

项目后续方向是联机对局，但当前没有网络层、协议层、房间、匹配、同步或断线恢复。进入实现前必须先确定权威模型和最小协议，避免本地规则与网络规则重复实现。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P3-1 | 选择权威模型 | 服务端权威、房主权威原型或客户端锁步取舍记录 | 明确作弊面、断线、重连和终局裁定影响 |
| P3-2 | 定义最小协议 | `JoinRoom`、`Ready`、`StartGame`、`SubmitMove`、`MoveAccepted`、`MoveRejected`、`BoardSnapshot`、`PlayerTimeout`、`Resign` | 每条协议映射到已有或计划中的领域事件 |
| P3-3 | 定义快照结构 | 棋盘尺寸、当前玩家、棋子状态、手顺、计时、最后一步、局面版本或 hash | 可用于重连或双端校验 |
| P3-4 | 明确网络与 Unity 边界 | 网络命令描述领域动作，不描述 prefab 或场景对象操作 | 网络层不直接实例化棋子 |
| P3-5 | 明确联机非目标 | 匹配、观战、排行榜、账号、复盘分享是否继续排除 | `ROADMAP.md` 非目标保持一致 |

### 阶段退出条件

- `ARCHITECTURE.md` 记录联机权威模型和同步边界。
- `ROADMAP.md` 移动或补充阶段 2 入口条件。
- `11-online-readiness.md` 更新协议、快照和剩余风险。

## P4：最小联机原型

### 背景

联机原型必须复用 P0 稳定后的规则入口，不能绕过本地落子校验，也不能让网络代码直接操作 Unity 预制体。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P4-1 | 接入最小传输或会话层 | 可启动的房间或会话原型 | 两个客户端可加入同一局 |
| P4-2 | 实现提交落子 | 客户端发送领域落子命令 | 非当前玩家或非法点被拒绝 |
| P4-3 | 实现接受/拒绝结果 | accepted 更新棋盘，rejected 显示原因 | 双端棋盘一致 |
| P4-4 | 实现快照同步 | 可请求或推送棋盘快照 | 断线后至少能安全退出或重新同步 |
| P4-5 | 保留本地对局入口 | 联机新增不替换本地对局 | 本地热座回归通过 |

### 阶段退出条件

- 两个客户端之间可以同步合法落子。
- 非法落子由权威端拒绝并返回原因。
- 双端有版本号或 hash 校验。
- 本地对局、电脑对局和 KataGo ownership 基线未被破坏。

## P5：终局与发布准备

### 背景

当前终局结算临时依赖 KataGo `ownership`，没有死子确认和完整线上裁定模型。发布前还需要明确 KataGo 引擎、模型、OpenCL/Eigen fallback、平台支持和资源分发策略。

### 任务表

| 编号 | 任务 | 交付物 | 验证 |
| --- | --- | --- | --- |
| P5-1 | 补死子确认流程 | 死子标记、确认、争议处理或继续对局路径 | 本地终局不只依赖 raw ownership |
| P5-2 | 明确线上裁定 | 权威端如何处理虚手、认输、超时、死子争议和最终结果 | 双端不会各自裁定不同结果 |
| P5-3 | 补复盘或记录入口 | 可读取记录文件并展示手顺或局面 | 保存记录可被用户使用 |
| P5-4 | 明确平台发布策略 | Windows PC、WebGL、移动端、KataGo 资源分发范围 | 平台非目标或目标写入路线 |
| P5-5 | 补发布前验证清单 | 本地、AI、联机、保存、资源包、KataGo fallback 检查 | 发布前有稳定回归路径 |

### 阶段退出条件

- 终局口径不再只依赖临时 ownership 结果。
- 线上裁定和本地终局差异被明确记录。
- 发布目标平台和非目标平台明确。
- 文档同步到 `SPECIFICATION.md`、`ARCHITECTURE.md`、`ROADMAP.md` 和相关模块文档。

## 当前建议执行顺序

1. 先执行 P0-1 至 P0-3：稳定落子命令、规则结果、真实落子应用点和悔棋回放应用点。
2. 再执行 P0-4 至 P0-5：补非法提示和规则回归。
3. P0 结束后统一收口文档，再进入 P1。
4. P1 结束后进入 P2，优先拆分 AI 与 UI 大类，降低后续功能追加成本。
5. 当前主线完成 P0-P2 前，不进入 P3 的正式联机架构决策。
6. P4 之前不要开始网络 SDK、传输层、房间、匹配、重连或任何实际联机功能实现。

## 阶段收口清单

每个阶段结束时检查：

- 行为是否改变；改变则更新 `SPECIFICATION.md`。
- 架构边界是否改变；改变则更新 `ARCHITECTURE.md`。
- 阶段目标、范围或非目标是否改变；改变则更新 `ROADMAP.md`。
- 模块入口、完成度或风险是否改变；改变则更新对应 `modules/` 文档。
- Unity C# 改动是否已经通过 Unity Editor 编译；无法执行时记录原因。
- 本地对局基线是否仍可回归。
- 是否留下新的临时调试路径、隐藏本地配置或未记录风险。
